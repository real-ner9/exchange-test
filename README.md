# Обмен заданиями с внешней системой

Тестовое задание «Обмен с внешней системой» (`task/04-system-integration.md`), вариант 4.

Внутренняя система принимает задания, внешний сервис их исполняет и сообщает результат. При сбоях
операторы повторяли отправку, инициаторы создавали дубли, состояние двух систем расходилось.
Эта версия решает три проблемы:

- **Инициатор видит, что происходит с заданием и нужно ли его действие.** Простые статусы,
  история изменений, понятная подсказка. Повторный клик не создаёт дубль.
- **Одна бизнес-операция исполняется ровно один раз.** Так происходит при любых повторах,
  потерянных ответах, перезапусках и параллельных отправщиках. Это проверяется независимо:
  эмулятор считает фактические исполнения.
- **Оператор восстанавливает управляемость при сбоях.** Для этого есть очередь проблем,
  ручной повтор, закрытие без подтверждения с причиной, полный журнал и сверка с внешней системой.

## Как проверить руками (демо-сценарии)

Сбои переключаются у оператора на странице **Демо-панель**. Она вызывает API эмулятора;
основное приложение о режимах сбоев не знает и видит только последствия.

1. **Обычный путь.** Войдите как `ivanov` и создайте задание. Статус сам меняется:
   «Отправляется» → «Принято в работу» (синий) → «Выполнено» (зелёный).
2. **Двойной клик.** Ключ формы (`clientRequestId`) создаётся при её открытии. Повторная отправка
   той же формы возвращает то же задание. Новая форма с тем же содержанием создаёт новое задание,
   но заранее предупреждает: «Похожее задание уже создано недавно».
3. **Недоступность.** Оператор включает «Недоступность», инициатор создаёт задание. Инициатор видит
   «Отправляется» и что действий не требуется. Оператор видит его «Ожидает повтора»: число попыток
   растёт, пауза между ними увеличивается. После выключения задание уйдёт само при следующей попытке.
   Можно не ждать и нажать «Повторить сейчас».
4. **Потеря ответа после исполнения.** Включите «Потеря ответа» и создайте задание. Отправщик не
   дождётся ответа и пометит попытку как «исход неизвестен». Перед следующей попыткой он запросит
   статус операции и повторно её не отправит. В карточке оператора кнопка «Сколько раз исполнено?»
   спрашивает эмулятор и показывает 1.
5. **Повтор и задержка результата.** Включите «Повтор результата» и «Задержку» с перестановкой.
   Итоговый результат придёт раньше «принято». На вкладке «Входящие результаты» видно: дубли
   проигнорированы, устаревшая версия проигнорирована, статус не откатился.
6. **«Закрыть без подтверждения».** Во время недоступности оператор закрывает задание, причина
   обязательна. Инициатор видит «Решается оператором», в отчёт о выполнении задание не попадает.
   После восстановления запустите **Сверку**. Появится расхождение «У нас закрыто вручную, у них не
   исполнялось», варианты решения: «Переотправить» или «Закрыть окончательно». Если внешняя система
   всё-таки исполнила операцию, задание само станет «Выполнено» с пометкой «подтверждено после
   ручного закрытия».
7. **Отказы.** Маркер `#reject` в названии при включённом «Отказе по содержанию» даёт 422.
   Инициатор видит «Требует решения» и кнопку «Создать исправленное задание».
   Маркер `#fail` при включённом «Отказе исполнения» даёт «Не выполнено».
8. **Два оператора.** Откройте одно задание у `operator` и `operator2` и нажмите действие у обоих.
   Второй получит «Задание уже изменилось, обновите карточку». Действует оптимистичная блокировка
   по версии записи.

Главное отступление от просьб заказчиков сделано в D02, D04 и D06: выполнить их буквально значило бы
показывать «Выполнено» без факта исполнения или откатывать статус задержанным сообщением.
Отчёт, экран и действия оператора обязаны отражать подтверждённое фактическое исполнение
(D02, D06 «внутреннее состояние всегда должно отражать фактическое исполнение»), поэтому
приоритет у этого требования. Открытые вопросы к заказчику — в конце этого файла.

## Архитектура

```
 Браузер ──► app-web (nginx + React) ──/api──► app-api (Spring Boot) ──► app-db (PostgreSQL)
                                                  │   ▲
                              POST /operations    │   │  POST /integration/results
                              GET  /operations/*  ▼   │  (результаты, с повторами)
                                               emulator (Spring Boot) ──► emulator-db (PostgreSQL)
```

- **app-api** — основной сервис: задания, outbox, отправщик, приём результатов, роли,
  действия оператора, сверка.
- **emulator** — отдельное приложение со своей БД и портом. Основное приложение знает о нём только
  контракт ([`docs/contract.md`](docs/contract.md)). Режимы сбоев хранятся в БД эмулятора и переживают
  его перезапуск. Таблица `executions` — независимый счётчик фактических исполнений.
- **app-web** — интерфейс. Роли разделены и на сервере (Spring Security), и в навигации.

### Путь задания

1. `POST /api/tasks`: задание и строка `outbox` пишутся в **одной транзакции**. Принятое задание
   не теряется ни при недоступности внешней системы, ни при перезапуске.
2. Отправщик (`Dispatcher` + `OutboxStore`) забирает созревшие строки через
   `FOR UPDATE SKIP LOCKED`, поэтому несколько потоков или экземпляров не возьмут одну строку.
   Взятая строка «арендуется» на 30 с. Если процесс упадёт посреди отправки, строку возьмут снова,
   а прошлая попытка останется незавершённой. Это сигнал перед повтором сначала спросить статус.
3. Каждая попытка получает новый `attemptId` с тем же `operationKey`. Исход классифицируется по
   таблице D05. HTTP-вызов идёт вне транзакции, а запись до и после него — в коротких транзакциях.
4. Результаты приходят на `POST /integration/results`. Каждое сообщение сначала фиксируется в `inbox`
   по уникальному `resultId`, затем применяется. Статус меняет только версия больше уже применённой.
5. Все источники сведений о внешнем состоянии меняют статус через одно место —
   `ExternalStateApplier`, с одинаковыми правилами. Источников четыре: ответ на отправку,
   проверка статуса, входящий результат и сверка.
6. Блокировки берутся в одном порядке: сначала строка outbox, потом строка задания. Поэтому
   отправщик, приём результатов и действия оператора не взаимоблокируются.

## Производительность

Профиль и критерии выбраны под вводную «5000 записей основного реестра и 20 одновременных пользователей».

- **Подготовка данных** (`load/seed.js`): 5000 заданий создаются через публичный API от 20 инициаторов.
  Каждое проходит реальный обмен (outbox → отправщик → эмулятор → результат). Измеряются время
  создания и время, за которое обмен «сливает» всю очередь.
- **Рабочий профиль** (`load/load.js`, 3 мин, 20 VU). 16 инициаторов: список своих заданий, карточка,
  создание (каждая 5-я итерация), отчёт (каждая 10-я). 4 оператора: сводка, очередь (разные
  вкладки и страницы), карточка с историей, журнал. Пауза 1 с между действиями — интерактивная работа людей.
- **Стресс** (`THINK=0`, 1 мин): те же 20 VU без пауз, чтобы оценить запас.
- **Критерии:** ошибок < 1 %, p95 всех запросов < 500 мс, p95 создания и списка заданий < 300 мс,
  ноль операций с повторным исполнением у эмулятора.

```bash
docker compose down -v && docker compose up -d --build
docker compose --profile load run --rm k6 run /scripts/seed.js
docker compose --profile load run --rm k6 run /scripts/load.js
docker compose --profile load run --rm -e THINK=0 -e DURATION=1m k6 run /scripts/load.js
```

В Git Bash на Windows перед командами нужен `MSYS_NO_PATHCONV=1`.

**Для какой работы этого достаточно.** 20 человек при интерактивной работе создают около 47 запросов
в секунду, а стенд держит около 1370 запросов в секунду без ошибок. Запас примерно тридцатикратный.
Реестр на 5000 заданий целиком проходит обмен меньше чем за минуту. Время ответа определяется
индексами (`tasks(initiator_id, created_at)`, `tasks(status, updated_at)`), а не объёмом.
Этого хватает для отдела в десятки пользователей и потока в тысячи заданий в день. Узкое место при
росте потока — исполнение и доставка результатов эмулятором, а не основное приложение.

**Что нашёл стресс-прогон.** В первой версии nginx открывал новое TCP-соединение к app-api на каждый
запрос. Примерно при 950 запросах в секунду кончились эфемерные порты, и половина запросов получила 502.
Исправлено keepalive-пулом к upstream (`app-web/nginx.conf`). Повторный прогон — 0 % ошибок.
Тот же прогон показал, что эмулятор исполнял и доставлял результаты в один поток (~70 в секунду);
воркеры распараллелены, это безопасно благодаря `SKIP LOCKED`.

**Чего эти измерения не показывают.** Нет работы на отдельных серверах с сетевой задержкой.
Нет длительной работы (часы) и не измерена деградация при росте журнала до миллионов событий.
Сверка не проверялась на больших объёмах: для 5000 заданий она занимает доли секунды.

## Стек

Java 21, Spring Boot 4.2 (MVC, Security, JDBC, Flyway), PostgreSQL 17, React 19 + TypeScript + Vite,
nginx, Docker Compose, JUnit 5 + Testcontainers, k6. Это предпочтительный стек заказчика.

- **SQL через JdbcClient, без ORM.** Ключевые места (`SKIP LOCKED`, `ON CONFLICT`, условные
  обновления по версии) видны в коде как есть, без скрытого поведения.
- **Оптимистичная блокировка вручную.** Сделана как `UPDATE … WHERE version = :expected`,
  потому что так её проще проверить и объяснить.
- **Без брокера сообщений.** Задание его не требует, а transactional outbox на PostgreSQL даёт ту же
  гарантию «принято — не потеряется» без лишнего компонента.

## Что уже работает и что требует решения

**Работает:**
- создание задания с защитой от дублей;
- реальный обмен с отдельным эмулятором;
- получение результатов с защитой от дублей и перестановки;
- повторы с классификацией ошибок;
- очередь и действия оператора с журналом;
- сверка и демо-панель сбоев;
- разграничение ролей на сервере;
- автотесты и нагрузочный прогон.

**Ограничения прототипа:**
- **Демо-авторизация.** Логин и пароль из БД, сессия в cookie. SSO и управления пользователями нет.
- **Приём результатов без аутентификации.** `/integration/results` защищён только сетью Docker.
  Для продакшена нужна подпись (HMAC) или mTLS — это надо согласовать с владельцем внешнего сервиса.
- **Сверка целиком в памяти.** Она грузит полный список операций внешней системы. Для тысяч и
  десятков тысяч операций этого хватает. Для миллионов нужна инкрементальная сверка по
  `updatedSince` с сохранённой отметкой.
- **Защита от параллельной сверки внутри одного процесса.** Сверка с нескольких экземпляров app-api
  одновременно не исключена: для этого нужна advisory-блокировка PostgreSQL.
- **Неразбираемый ответ проверен только тестами.** Эмулятор неразбираемых ответов не шлёт, поэтому
  путь `NEEDS_ATTENTION` проверен в автотестах (`FakeExternal`), а в демо через UI не воспроизводится.
- **Нет уведомлений.** Инициатор узнаёт о смене статуса на экране (автообновление раз в 3 с),
  письма и push не отправляются.

**Открытые вопросы к заказчику** (ответов за время работы не было; действуем по допущениям из `docs/decisions.md`):
1. Можно ли назвать кнопку «Закрыть без подтверждения» вместо «Считать выполненным» (D06)?
   Если нет, меняется только надпись: поведение останется прежним, потому что иначе отчёт врёт.
2. Устроит ли инициатора синяя отметка «Принято в работу» вместо зелёной (D02)?
3. Готов ли владелец внешнего сервиса дедуплицировать по стабильному `operationKey` при новом
   `attemptId` на каждую попытку (D03/D04)? Без этого гарантия «один раз» невозможна при потере ответа.
4. Подходят ли пороги «долго не проходит» — 10 попыток или 30 минут (D05)? Настраиваются в
   `application.properties`.
