# Решения по спорным вводным

Каждое решение должно быть видно и здесь, и в поведении сервиса: статус, кнопка, запись в журнале, тест.

## Подробно

### D01. Двойной клик и честные дубли
- Фронт генерирует `clientRequestId` (UUID) при открытии формы и отправляет его с созданием.
- `UNIQUE(initiator_id, client_request_id)`. Повтор с тем же ключом возвращает уже созданное задание (200, не 201), второе не создаётся.
- Новая форма даёт новый ключ, значит одинаковое по содержимому задание создаётся. Перед созданием показываем «Похожее задание создано 3 мин назад» — инициатор решает сам.
- Кнопка блокируется на время запроса, но защита держится на сервере, не на кнопке.

### D02. Что видит инициатор
Пользовательские статусы (технические детали — только у оператора):

```
statuses[6]{user_status,color,needs_action,internal_states}
Отправляется,серый,нет,"NEW, QUEUED, SENDING, RETRY_WAIT"
Принято в работу,синий,нет,ACCEPTED
Выполнено,зелёный,нет,COMPLETED
Не выполнено,красный,да,"FAILED (внешняя система вернула отказ исполнения)"
Требует решения,жёлтый,да,"REJECTED (отказ по содержанию) — исправить и создать заново"
Решается оператором,жёлтый,нет,"NEEDS_ATTENTION, MANUALLY_CLOSED"
```

Отчёт о выполнении строится только по `COMPLETED`. Расхождение с просьбой D02 объясняем в README: зелёная отметка на «получено» привела бы к тому, что отчёт и экран показывают разное.

### D03 + D04. Идентификаторы
- `operation_key` — один на задание, создаётся при принятии задания, никогда не меняется. По нему внешний сервис дедуплицирует исполнение.
- `attempt_id` — новый на каждую отправку. Это и есть «новый идентификатор при каждой повторной отправке» для трассировки, но исполнение к нему не привязано.
- Если ответ на отправку потерян, перед повтором запрашиваем `GET /operations/{key}`: если операция уже принята или исполнена — не отправляем снова.

### D04. Порядок результатов
- Каждый результат от эмулятора несёт `resultId` и `version` (монотонный номер в рамках операции).
- Повтор того же `resultId` → журнал «дубликат», без изменений.
- `version` меньше уже применённой → журнал «устаревший», без изменений.
- Терминальные статусы не откатываются в нетерминальные.
- Почему не «последний пришедший»: сценарий «результат Выполнено пришёл, потом задержанное Принято» вернул бы задание назад в работу.

### D05. Повторы и классификация ошибок

```
errors[5]{case,class,action}
"таймаут, обрыв соединения",временная,"сначала GET статуса, потом повтор"
"503 / 502 / 504",временная,"повтор с backoff 1s → 2s → … → потолок 5 мин"
"429",временная,"повтор с учётом Retry-After"
"422 отказ по содержанию",постоянная,"REJECTED, без повтора, видно инициатору и оператору"
"неразбираемый ответ",постоянная,"NEEDS_ATTENTION, оператор смотрит сырой ответ"
```

Повтор временных ошибок бесконечный, как просили. Но после 10 попыток или 30 минут задание дополнительно попадает в очередь оператора с пометкой «долго не проходит», чтобы о нём знали. Ручной повтор оператора сбрасывает таймер backoff и создаёт новую попытку с тем же `operation_key`.

### D06. «Считать выполненным»
- Кнопка называется «Закрыть без подтверждения», в подсказке — «бывшее Считать выполненным». Причина обязательна.
- Статус `MANUALLY_CLOSED`: повторы останавливаются, задание уходит из рабочей очереди, в отчёт о выполнении не попадает.
- Сверка после восстановления связи: если эмулятор сообщает, что операция исполнена → `COMPLETED` с пометкой «подтверждено после ручного закрытия»; если нет → расхождение в отчёте сверки, оператор решает (переотправить или закрыть окончательно).
- Каждое действие оператора — в журнал: кто, когда, причина, состояние до и после.

### D07. Надёжность и роли
- Создание задания и запись в `outbox` — одна транзакция. Отправщик забирает записи через `SELECT … FOR UPDATE SKIP LOCKED`, поэтому несколько воркеров и перезапуск безопасны.
- Входящие результаты пишутся в `inbox` с уникальным `resultId` до обработки.
- Сверка: эмулятор отдаёт `GET /operations?updatedSince=…`; сервис сравнивает статусы и показывает расхождения: «у нас Отправляется, у них Выполнено», «у нас закрыто вручную, у них не исполнялось» и т.д.
- Роли: `INITIATOR` видит и создаёт только свои задания; `OPERATOR` видит очередь обмена, журнал и сверку, не создаёт задания от чужого имени. Проверки на сервере, тесты на 403.
- Оптимистичная блокировка (`version` у задания) против одновременных действий двух операторов.

### D08. Эмулятор
- Отдельное приложение, отдельная БД, свой порт. Основное приложение знает о нём только по контракту.
- Режимы (переключаются через `POST /admin/faults` и в UI оператора на демо-панели):

```
faults[6]{mode,behaviour}
unavailable,"на любой запрос 503"
lose_response,"операция принята и исполнена, но ответ на отправку обрывается"
duplicate_result,"результат отправляется дважды"
delay_result,"результат приходит через N секунд; можно переставить порядок"
reject_content,"задания с определённым признаком получают 422"
fail_execution,"задания с определённым признаком исполняются с отказом (outcome=FAILED)"
```

`fail_execution` нет во вводных D08. Он добавлен, чтобы в демо можно было получить статус «Не выполнено» (FAILED) из D02: без него эмулятор никогда не возвращает отказ исполнения.

- `GET /admin/operations/{key}/executions` — сколько раз операция фактически исполнялась. Тесты и демо проверяют, что это всегда 1.

## Контракт внешнего сервиса (черновик)

```
endpoints[5]{method,path,purpose}
POST,/operations,"отправка; тело {operationKey, attemptId, payload}; 202 accepted / 200 already_known / 422 / 503"
GET,/operations/{operationKey},"статус операции для проверки после потерянного ответа"
GET,/operations?updatedSince=,"список для сверки"
POST,{callbackUrl}/results,"эмулятор → сервис: {resultId, operationKey, version, outcome, executedAt}"
POST,/admin/faults,"управление сбоями эмулятора"
```
